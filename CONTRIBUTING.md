# Contributing to odctl

This file is for people who change odctl itself: the CLI, its compose files and images, its tests and its documentation. To use odctl, start with the [documentation](https://jaehyeon.me/odctl/). For a change larger than a fix, such as a new profile, open an issue first, so the design is agreed before the work starts. The [roadmap](https://jaehyeon.me/odctl/latest/about/roadmap/) shows what is planned, and [How It Works](https://jaehyeon.me/odctl/latest/how-it-works/) shows how the parts fit together.

## Set Up

odctl uses [uv](https://docs.astral.sh/uv/) and needs Docker. Clone the repository, install the dependencies and the project in development mode, and install the pre-commit hooks, which run the formatting and type checks on each commit:

```bash
git clone https://github.com/jaehyeon-kim/odctl.git
cd odctl
uv sync
uvx pre-commit install
```

Exporting the diagrams also needs draw.io, Chrome and ffmpeg.

## Tests

```bash
uv run pytest tests/ -q
uvx pre-commit run --all-files                    # ruff, ruff format, mypy, whitespace, YAML, TOML
DISABLE_MKDOCS_2_WARNING=true uv run mkdocs build --strict
uv run mkdocs serve -a 127.0.0.1:8000             # docs at http://127.0.0.1:8000/odctl/
uv run python scripts/gen_pages.py                # regenerate skills/odctl/SKILL.md
uv run python scripts/diagrams.py [name ...]      # export diagrams; needs draw.io, Chrome and ffmpeg
```

Each layer checks one thing:

- `tests/` checks the CLI, the registry, the compose files, the docs and the generated pages, with no container running.
- The strict docs build fails on a broken link or anchor.
- The e2e tests start each profile group and run `.github/scripts/smoke.sh` on it. A running container is not enough: the script checks that the profile does its job, such as a Kafka consumer reading a message or a Flink job committing to Iceberg. It also runs each guide's snippets and Runnable Example.

Run the unit suite in full once before each commit. While fixing, run only the failed tests (`pytest --lf`) and the tests of the files you changed. Run the strict build when `docs/`, `mkdocs.yml` or an input of `scripts/gen_pages.py` changed: `registry.yml`, a compose file, or a command's `--help` text.

A pull request runs pre-commit, the unit tests on each supported Python version, the strict docs build, and the image builds when an image input changed. e2e runs only on a tag and on a manual run, because odctl runs images tagged with its own version, and the images of an unreleased version do not exist yet. To check a profile on your machine, do what the e2e job does: install the CLI with `uv tool install .`, run `odctl init`, start the profile with `odctl up <profile>`, then run `.github/scripts/smoke.sh <profile>`. Run one `odctl up` at a time. When no image definition changed since the last release, you can give the last release's images the new version's tag for the test, and remove those tags afterwards.

## Rules

- **Images follow the CLI version.** odctl runs its own images at its own version (`TAG`), never `latest`: Docker does not pull a tag it already has, so a cached `latest` keeps running old code. Third-party images are pinned to a version and updated by Renovate.
- **Bind to 127.0.0.1.** Every published port binds to `127.0.0.1`, not all interfaces.
- **One profile per tool**, with `-lite` and `-full` variants where a tool has a small and a clustered form (`kafka-lite`, `kafka-full`).
- **Fixed container names.** Every service has a `container_name`, so `odctl up` cannot scale a service; several copies are separate named services (Flink's `taskmanager-a` and `taskmanager-b`).
- **A feature merges only with its docs.** Each command, option, profile and `.env` key needs a tested example on a guide, Getting Started or How It Works, a reference entry (the CLI reference, a profile page or How It Works), and a place in the skill; a command also needs a line in the README's Commands section. `test_every_feature_has_its_docs` checks this, and its short list of exceptions gives a reason for each.
- **Renovate** opens its pull requests on Mondays, with image updates grouped by compose file. Agree a change to its configuration (`.github/renovate.json`) with the maintainer first.

## Add a Profile

1. Add the services to the compose file of their area in `src/odctl/resources/`, following the Rules: a pinned image, a `container_name`, and ports bound to `127.0.0.1`.
2. Add the profile to `src/odctl/resources/registry.yml`: its compose file, description, profiles, dependencies, role and usage text. `scripts/gen_pages.py` builds its page from this entry and the compose file.
3. Add its checks to `.github/scripts/smoke.sh`, and its group to `GROUPS` in `.github/scripts/select-profiles.py`.
4. Add the technology to the README diagram, `image/diagram.drawio`, then export it. `test_readme_diagram_names_every_technology` fails until you do.
5. Give it a tested example on a guide, Getting Started or How It Works, then run `scripts/gen_pages.py` to update the skill.

## Add a Command or Option

Add it to `src/odctl/main.py` with its `--help` text, which the CLI reference is built from. Give it a tested example on a guide, Getting Started or How It Works, and a command a line in the README's Commands section. Then run `scripts/gen_pages.py` to update the skill.

## Write the Docs

- **Generated pages.** The profile pages and the CLI reference are generated by `scripts/gen_pages.py` during the build, from `registry.yml`, the compose files and the commands. Change those, not the pages, and do not copy versions or ports into hand-written guides.
- **Code blocks are copies.** Guide code lives in `docs/snippets/<guide>/`, one section per step (`# --8<-- [start:name]`), and Getting Started and How It Works follow the same rule. A block labelled `title="path:section"` or `title="path"` is a copy of that section or file, checked by `tests/test_docs.py`. Pages use copies, not `--8<--` includes, so the Markdown reads correctly on GitHub. Every guide ends with a Runnable Example, `example.sh` or `example.py` in its folder. `smoke.sh` runs the same sections and examples, and `select-profiles.py` maps each snippet folder to the e2e groups that run it.
- **Guides.** Each guide says which pages it builds on, the output of every step, and where a value it quotes is set. A page has at most 10 `##` headings and 15 in all.
- **Writing.** Plain English for readers whose first language is not English. Headings use title case, keeping product names such as `odctl` as they are, and do not start with "The". No em or en dashes. Each Markdown paragraph is one line, never hard-wrapped.
- **Diagrams.** Copy shapes from `docs/assets/diagrams/_legend.drawio`, and export with `scripts/diagrams.py`.

## Pull Requests

Work on a branch from `main` and open a pull request against `main`. Before you push, run pre-commit, the unit tests, and the strict build when the docs changed. Describe each change to ports, profiles, `.env` keys, volumes or workspace files in the pull request, so that the release can add an Upgrading line to the Changelog (`docs/about/changelog.md`).

## Releases

The maintainer releases. These steps are written down so that each release is the same:

1. Bump `version` in `pyproject.toml`, run `uv lock`, and add the release to `docs/about/changelog.md`, with an Upgrading line for any change to ports, profiles, `.env` keys, volumes or workspace files. When it reaches `main`, the docs deploy as that version, aliased `latest`.
2. Once the `main` pipeline for that commit is green, push tag `vX.Y.Z` on it. A tag on a commit whose checks fail builds no images and cannot be released until it is moved. The tag pipeline builds and pushes the `X.Y.Z` images, then runs e2e for every profile group (about an hour).
3. Publish the GitHub release with that version's Changelog section as its text, so the two never differ: `python scripts/release_notes.py X.Y.Z > /tmp/notes.md`, then `gh release create vX.Y.Z --title vX.Y.Z --notes-file /tmp/notes.md`. `publish.yml` waits for a green tag pipeline and checks that every `X.Y.Z` image is in ghcr, then uploads to PyPI.
